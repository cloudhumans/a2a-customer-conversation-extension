# A2A Customer Conversation Extension, v1

| | |
|---|---|
| **URI** | `https://cloudhumans.github.io/a2a-customer-conversation-extension/v1` |
| **Status** | Draft |
| **Base protocol** | [A2A](https://a2a-protocol.org/) 1.0 |
| **Extension type** | Profile extension (metadata only, no new RPC methods, no new task states) |
| **Dependencies** | None |

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## 1. Purpose

A2A lets agents exchange messages and tasks, but it has no notion of the **customer conversation** that usually surrounds those messages: a person talking to a business over chat, email, WhatsApp or voice, for support or for sales. Two things are missing whenever an agent takes part in such a conversation:

1. **Conversation context.** Which conversation in the client's system this message belongs to, who the customer is, and on which channel they are talking.
2. **Turn outcome.** Whether the agent answered, resolved the conversation, or needs a human to take over, and what that human should know.

This extension adds both, using only the `metadata` maps that A2A already defines. An agent or client that does not implement it keeps working as plain A2A.

## 2. Roles

- **Client**: the A2A client. Typically the system that owns the customer conversation (a helpdesk, a CRM, an orchestrating agent).
- **Agent**: the A2A server that takes a turn in that conversation.

The extension is symmetric: the same organization can be a client towards one agent and an agent towards another client.

## 3. Declaration

An agent that supports this extension declares it in its Agent Card:

```json
{
  "capabilities": {
    "extensions": [
      {
        "uri": "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1",
        "description": "Customer conversation context and turn outcomes (answered, resolved, needs human).",
        "required": false
      }
    ]
  }
}
```

- Agents SHOULD declare the extension with `required: false`, so that extension-unaware clients can still call them.
- v1 defines no `params`. Agents MUST NOT rely on `params` being read by clients.

## 4. Activation

- A client activates the extension by sending the URI in the `A2A-Extensions` HTTP header, as defined by the A2A extension activation rules.
- An agent that activates the extension SHOULD echo the URI in the `A2A-Extensions` response header.
- Because every key defined here is namespaced by the extension URI, an agent MAY honor the request keys of section 5 even when the header is absent. An agent MUST NOT treat the absence of these keys as an error unless it declared the extension with `required: true`.

## 5. Data sent by the client

All keys live in `Message.metadata` of the message the client sends (`SendMessage`). The key is the extension URI followed by `/` and the field name. In the table, `{ext}` stands for `https://cloudhumans.github.io/a2a-customer-conversation-extension/v1`.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `{ext}/conversationId` | string | yes, when the extension is active | Identifier of the conversation **in the client's system** (ticket, chat, thread). Stable for the whole conversation. |
| `{ext}/tenant` | string | no | Account, workspace or project the conversation belongs to in the client's system. |
| `{ext}/contact` | object | no | The customer. See 5.2. |
| `{ext}/channel` | string | no | Channel the customer is using. See 5.3. |

### 5.1 `conversationId` and `contextId`

A2A's `contextId` groups the tasks and messages that the **agent** considers part of one interaction, and is usually generated by the agent. `conversationId` is the **client's** identifier for the customer conversation. They are different things and both are kept:

- The client MUST send the same `conversationId` on every message of a conversation.
- The client SHOULD reuse the `contextId` returned by the agent on later messages of the same conversation, as A2A recommends.
- The agent SHOULD keep a single `contextId` per `conversationId` for a given client, and SHOULD echo `conversationId` in its response (section 6).

### 5.2 `contact`

```json
{
  "id": "string, the customer's identifier in the client's system",
  "name": "string",
  "email": "string",
  "phone": "string, E.164 recommended"
}
```

All fields are optional. Clients SHOULD send `id` whenever they send `contact`.

### 5.3 `channel`

Free-form string. Recommended values: `chat`, `email`, `whatsapp`, `voice`, `sms`, `social`, `api`. Agents MUST accept unknown values.

## 6. Data returned by the agent

When the extension is active, the agent reports the outcome of its turn in `Task.metadata` of the task it returns. If the agent replies with a `Message` instead of a `Task`, the same keys go in that `Message.metadata`.

| Key | Type | Required | Meaning |
|---|---|---|---|
| `{ext}/outcome` | string | yes, on a terminal task | `answered`, `resolved` or `needsHuman`. See 6.1. |
| `{ext}/handoff` | object | yes, when `outcome` is `needsHuman` | See 6.2. |
| `{ext}/conversationId` | string | no | Echo of the client's `conversationId`. |

### 6.1 Outcomes

A2A does not allow extensions to add task states, so the outcome is carried in metadata on top of a normal state.

| `outcome` | `TaskState` | Meaning |
|---|---|---|
| `answered` | `TASK_STATE_COMPLETED` | The agent produced its reply for this turn. The conversation continues. A question back to the customer is also `answered`. |
| `resolved` | `TASK_STATE_COMPLETED` | The agent replied and considers the conversation resolved. The client MAY close it. |
| `needsHuman` | `TASK_STATE_COMPLETED` | The agent stops here and asks the client to hand the conversation to a human. The reply parts, if any, are what the agent wants the customer to see before the handoff. |

Rules:

- An agent SHOULD end each turn with `TASK_STATE_COMPLETED` and an `outcome`, and SHOULD NOT use `TASK_STATE_INPUT_REQUIRED` to mean "waiting for the customer" or "waiting for a human". In A2A, `input-required` asks the **client** for more input on the same task, and generic clients act on it that way.
- `TASK_STATE_FAILED`, `TASK_STATE_REJECTED`, `TASK_STATE_CANCELED` and `TASK_STATE_AUTH_REQUIRED` keep their A2A meaning. They carry no `outcome`. A client MAY decide on its own to hand the conversation to a human after a failure.
- A client that receives a completed task without `outcome` MUST treat it as `answered`.

### 6.2 `handoff`

```json
{
  "note": "string, required. What the human taking over needs to know: what the customer wants, what was already tried, what is pending.",
  "reason": "string, optional. Short machine-readable reason, for example customer_request, out_of_scope, policy, low_confidence, out_of_office."
}
```

The `note` is written for the human agent, not for the customer. Clients MUST NOT show it to the customer.

## 7. Examples

### 7.1 Request

```http
POST /a2a HTTP/1.1
Content-Type: application/json
A2A-Version: 1.0
A2A-Extensions: https://cloudhumans.github.io/a2a-customer-conversation-extension/v1
Authorization: Bearer <token>

{
  "jsonrpc": "2.0",
  "id": "1",
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "6f1c0a52-8d0e-4c1f-9d55-3d9a1a0b2e11",
      "role": "ROLE_USER",
      "parts": [{"text": "Meu rastreador parou de atualizar desde ontem."}],
      "metadata": {
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/conversationId": "48213",
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/tenant": "acme",
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/channel": "whatsapp",
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/contact": {
          "id": "c-991",
          "name": "Maria Souza",
          "phone": "+5511999990000"
        }
      }
    },
    "configuration": {"returnImmediately": false}
  }
}
```

### 7.2 Response: the agent answered

```json
{
  "jsonrpc": "2.0",
  "id": "1",
  "result": {
    "task": {
      "id": "t-1",
      "contextId": "ctx-77",
      "status": {"state": "TASK_STATE_COMPLETED"},
      "artifacts": [{"artifactId": "a-1", "parts": [{"text": "Consegui ver que o equipamento está sem sinal desde 18h. Ele está em área coberta?"}]}],
      "metadata": {
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/outcome": "answered",
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/conversationId": "48213"
      }
    }
  }
}
```

### 7.3 Response: the agent needs a human

```json
{
  "jsonrpc": "2.0",
  "id": "2",
  "result": {
    "task": {
      "id": "t-2",
      "contextId": "ctx-77",
      "status": {"state": "TASK_STATE_COMPLETED"},
      "artifacts": [{"artifactId": "a-2", "parts": [{"text": "Vou te transferir para um especialista."}]}],
      "metadata": {
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/outcome": "needsHuman",
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/handoff": {
          "note": "Rastreador sem sinal desde 18h de ontem, cliente confirma área coberta. Precisa de abertura de visita técnica.",
          "reason": "out_of_scope"
        },
        "https://cloudhumans.github.io/a2a-customer-conversation-extension/v1/conversationId": "48213"
      }
    }
  }
}
```

## 8. Security

- Every key in this extension is input from the other party and MUST be validated.
- `tenant` is a hint, not an authorization. An agent MUST authorize the caller from its authenticated identity (for example the OAuth2 `client_credentials` client) and MUST reject a `tenant` the caller is not allowed to act on. When the credential is bound to a single tenant, the agent SHOULD ignore `tenant`.
- `conversationId` and `contact.id` MUST NOT be used as credentials or to reach data across tenants.
- `contact` carries personal data. Agents SHOULD store only what they need and follow the data protection rules that apply to the client.

## 9. Versioning

- This document defines `v1`. Any breaking change gets a new URI (`/v2`), as A2A requires. Agents MUST NOT fall back from one version to another.
- Adding an optional field or a new `handoff.reason` value is not a breaking change. Clients and agents MUST ignore keys and values they do not know.

A machine-readable JSON Schema of the metadata values is available in [`schema.json`](schema.json).
